## 三、从数据里能看出什么

### 1. Generate 稳定在 ~5 tok/s，和输入长度无关

三次测试分别是 5.07 / 5.05 / 4.86，几乎不动。

这正是 **memory-bound** 的典型特征：decode 阶段每次只算一个 token，但要把整个模型的权重从内存搬一遍，瓶颈在**带宽**不在算力。所以不管前面堆了多少上下文，出字速度都是这个数。

**推论**：想提升出字速度，方向是「减少要搬的数据量」——量化（w8a8 → w4a16）、或换更小的模型。加算力没有用。

### 2. Prefill 越长越高效（43 → 92 tok/s）

13 个 token 时 43.63 tok/s，475 个 token 时 92.32 tok/s，**效率翻倍**。

这是 **compute-bound** 的特征：prefill 把所有输入位置并行计算，输入越长越能填满 NPU，吞吐自然上去；短输入则被固定开销拖累。

**推论**：长输入不会等比例变慢。475 token 的输入用了 5.1 秒，而不是 13 token 的 36 倍。

### 3. 真正的体验瓶颈在 prefill

你的应用（知识图谱 + RAG 拼上下文）大概率会喂进去几百到上千 token。按现在的速度：

```
输入 475 token  →  等 5.1 秒才开始出字
输入 2000 token →  预计等 20 秒以上
```

对一个大屏演示来说，这段"没反应"的时间比出字慢更难受。**优化 prefill 的收益比优化 decode 更直接。**

### 4. 内存占用 4.57 GB，很稳定

不管输入多长，峰值都是 4.56–4.57 GB。板子有 16 GB，**内存不是瓶颈**。

（加载前后系统可用内存从 14.6 GB 降到 9.9 GB，差值 4.7 GB，和模型文件大小吻合。）

## 四、和官方数据的对照

官方 benchmark（RK3588，输入 128、输出 64，w8a8）：

| 模型 | TTFT | 速度 | 内存 |
|---|---|---|---|
| Qwen3.5-0.8B | 588 ms | 27.05 tok/s | 1.0 GB |
| Qwen3.5-2B | 777 ms | 13.59 tok/s | 2.1 GB |
| Qwen3.5-4B | 2069 ms | **6.22 tok/s** | 4.6 GB |
| **你的 Qwen3-4B** | — | **5.07 tok/s** | **4.57 GB** |

> 注意：官方跑的是 Qwen3.5-4B（混合注意力），你跑的是 Qwen3-4B（标准注意力），**不是同一个模型**，只能算量级参照。
>
> 内存几乎一致（4.6 GB），速度你的略低。考虑到你的驱动版本偏低（0.9.6 < 0.9.7）、runtime 也旧（1.2.3），这个差距是合理的。

## 五、可优化项（按性价比排序）

| # | 措施 | 预期收益 | 风险/成本 |
|---|---|---|---|
| 1 | 升级 RKLLM runtime 1.2.3 → 1.3.0 | 中 | 低，只需换 `librkllmrt.so` |
| 2 | 升级 NPU 驱动 0.9.6 → 0.9.7+ | 中高 | **高**，要动内核/固件，可能变砖 |
| 3 | 输入侧做上下文裁剪（RAG 少拼一点） | 高（直接降 TTFT） | 低，但要牺牲召回 |
| 4 | 换 w4a16 量化 | 内存减半；速度待测 | 中，要重新转换模型 |
| 5 | 减小 `max_context_limit`（现 4096） | 低 | 低，但限制功能 |

**建议顺序：1 → 3 → 4。** 第 2 项风险太高，除非有官方固件升级包，否则别碰。

## 五点五、端到端实测：优化提示词模板（2026-10-08）

### 背景

前面几组测的是直接调 RKLLM 接口。这一次测**真实业务链路**：
后端拼 prompt → 调 RKLLM → 生成整份故障报告。

来源：`POST /api/report/generate`，故障项 `INS_BRAKE_001` + 状态 `STATE_BRAKE_002`。

### 优化前

```
Prefill    223 token   2307.76 ms    96.63 tok/s
Generate   552 token  112371.60 ms    4.91 tok/s
端到端     114.9 秒
报告长度   2406 字
```

### 优化动作

只改了一处：`backend/app/services/report_service.py` 里的 `system_prompt`。

原模板只说"逐项分析""按严重程度列出"，**没有任何长度约束**，模型自由发挥写到 2400 字。

新模板加了：

```
【长度要求】全文控制在 1200 字以内，语言精炼，不要重复罗列同一条风险。

## 故障原因分析   用 2-3 句话说明根本原因和演化路径，不超过 250 字。
## 风险评估       只列最关键的风险项及其后果，不超过 200 字。
## 整改建议       按紧急程度列 2-3 条措施，不超过 200 字。
## 综合结论       一句话给出综合评价，不超过 80 字。
```

### 优化后

```
Prefill    255 token   2663.77 ms    95.73 tok/s
Generate   149 token  29893.85 ms    4.98 tok/s
端到端      32.8 秒
报告长度    674 字
```

### 前后对比

| 指标 | 改前 | 改后 | 变化 |
|---|---|---|---|
| Generate token 数 | 552 | **149** | **-73%** |
| 生成耗时 | 112.4 s | **29.9 s** | **-73%** |
| 端到端耗时 | 114.9 s | **32.8 s** | **-71%** |
| 报告字数 | 2406 | 674 | -72% |
| 出字速度 | 4.91 tok/s | 4.98 tok/s | 不变 |

### 结论

**出字速度是硬件上限，改不动。唯一能优化的是「生成多少 token」。**

在 5 tok/s 的约束下：

```
耗时(秒) ≈ 输出 token 数 ÷ 5
```

所以提示词的**长度约束直接等于时间**。这一刀砍掉 73% 的时间，成本是零（改几行字符串）。

**剩余可调空间**：674 字偏精简。如果想更详细，把各段字数上限放宽到 350/250/250/100，预计 950 字左右、约 45 秒。这是一个"详细程度 ↔ 等待时间"的取舍，按演示需要选。

> ⚠️ 注意：`flask_server.py` 的 `max_new_tokens` 当前设为 **1024**。
> 之前设 512 时报告会被截断（自然长度 552 > 512）。
> **如果以后又放宽提示词让报告变长，记得同步调大这个值**，否则会截断。

## 六、复现方法

```bash
# 1. 推送并执行重启脚本（打开 RKLLM 性能日志）
adb push scripts/01-重启服务并开日志.sh /userdata/rkllm/bench_start.sh
adb shell "sh /userdata/rkllm/bench_start.sh"

# 2. 电脑上转发端口
adb forward tcp:18080 tcp:8080

# 3. 发请求（OpenAI 格式）
curl -X POST http://127.0.0.1:18080/rkllm_chat \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"你好"}],"stream":false}'

# 4. 读性能数据
adb shell "grep -A3 'Prefill\|Generate\|Peak Memory' /userdata/rkllm/bench.log"
```

日志里每次推理都会打印一个统计块：

```
Stage         Total Time (ms)  Tokens    Time per Token (ms)      Tokens per Second
Prefill       297.94           13        22.92                    43.63
Generate      14014.78         71        197.39                   5.07
Peak Memory Usage (GB)
4.56
```
