# 03 · 知识库规模对推理速度的影响（实测）

> 测试日期：2026-10-08
> 目的：回答"Neo4j 知识库越来越大，会不会拖慢推理"
> 方法：往 prompt 里注入不同数量的图谱格式内容，模拟查询结果变多

---

## 一、测试设计

Neo4j 变大**只会通过一条路径**影响推理速度：

```
图变大 → 查询结果行数变多 → 拼出的 prompt 变长 → 推理变慢
```

所以直接构造不同长度的、**格式与真实图谱输出完全一致**的 prompt，
绕开数据库只测"prompt 长度 → 推理速度"这一段。

注入的每行内容：

```
制动器：制动力下降(性能退化)；现象：制停距离延长；风险：轿厢非正常移动、溜车风险；建议：更换制动衬垫
```

## 三、结论：对 prefill 是灾难，对 decode 只是轻微

### 1. Prefill —— 超线性增长，是真正的风险

```
76 token   →  0.92 s
993 token  →  16.71 s     ← 输入涨 13 倍，耗时涨 18 倍
```

**耗时增长比输入增长还快。** 拟合出来大约是：

```
prefill 耗时 ∝ token 数 ^ 1.3
```

原因：attention 的复杂度是 **O(n²)**——每个 token 都要和前面所有 token 做注意力计算。
序列越长，这部分占比越重，所以整体呈超线性。

**外推预测：**

| prompt token | 预计 prefill 耗时 |
|---|---|
| 250（你现在） | ~2.6 s |
| 500 | ~6.7 s |
| 1000 | ~16.7 s（实测） |
| **2000** | **~41 s** ← 不可接受 |

### 2. Decode —— 温和下降

```
76 token 上下文  →  5.12 tok/s
993 token 上下文 →  4.33 tok/s     ← 下降 15%
```

原因：decode 每步要读的不只是 4.85 GB 权重，还有**随上下文增长的 KV cache**：

```
KV cache = 144 KB/token × 上下文长度
993 token 时 = 143 MB（占权重总量的 2.9%）
```

加上 attention 计算本身的开销，所以 decode 慢了一点，但**远没到灾难级别**。

同理，即使上下文拉到 4096（`max_context_limit`），decode 最多再降 15% 左右。

## 四、对你项目的实际影响

现在后端拼出的 prompt 是 **223–255 token**，prefill 只用 2.3–2.7 秒，
**这块目前完全没问题**。

但如果知识库继续变大，风险在这里：

| 知识库规模 | prompt 估算 | prefill | 端到端（+30 秒生成） |
|---|---|---|---|
| 现在 | ~250 token | 2.6 s | ~33 s |
| 涨 2 倍 | ~500 | 6.7 s | ~37 s |
| **涨 4 倍** | **~1000** | **16.7 s** | **~47 s** |
| 涨 8 倍 | ~2000 | ~41 s | ~71 s |

**知识库涨 4 倍，端到端就从 33 秒变成 47 秒**——而且 prefill 那 16.7 秒用户是**完全没反应**的
（图谱数据在第 1 阶段已经渲染完了，用户盯着"正在连接模型..."发呆 16 秒）。

## 五、防护措施（按优先级）

### ① 限制查询返回量（最有效）

你的 Cypher 有 **13 个 `OPTIONAL MATCH`**，行数是它们的笛卡尔积。
在查询里直接过滤：

```cypher
OPTIONAL MATCH (s)-[:EVOLVES_TO]->(evolved:State)
WHERE evolved.severity >= 3          // 只要严重度高的演化
...
OPTIONAL MATCH (p)-[:LEADS_TO]->(r:RiskEvent)
WHERE r.risk_level >= 3              // 只要高等级风险
...
LIMIT 200                            // 兜底
```

### ② 冲突时按严重度截断（在拼 prompt 之前）

后端 `_build_prompt` 里对每个 state 的现象/风险/建议做**数量上限**：

```python
if s.phenomena: parts.append("现象：" + "、".join(p.name for p in s.phenomena[:3]))
if s.risks:     parts.append("风险：" + "、".join(r.name for r in s.risks[:3]))
```

取最严重的 3 条，通常不影响报告质量，但能显著压缩 prompt。

### ③ 监控 prompt 长度（长期）

在 `_build_prompt` 里加一行日志，超过阈值就告警：

```python
if len(data_text) > 3000:
    logger.warning("prompt 过长: %d 字符", len(data_text))
```

这样知识库膨胀时你能第一时间发现，而不是等到用户抱怨慢。
