## 改动 1：提示词加长度约束

**文件**：`backend/app/services/report_service.py` 的 `_build_prompt()`

**问题**：

报告生成耗时 114.9 秒。经实测，瓶颈 100% 在 decode（写报告），
prompt 只有 223 token，prefill 仅 2.3 秒。

**原因**：原模板只说"逐项分析""按严重程度列出"，**没有任何长度约束**，
模型自由发挥写到 2406 字（552 token），按 4.91 tok/s 算就是 112 秒。

**改动**：

```diff
 报告模板：
 综合安全状况等级：X级

+【长度要求】全文控制在 1200 字以内，语言精炼，不要重复罗列同一条风险。
+
 ## 故障原因分析
-逐项分析不合格项的根本原因和故障演化路径。
+用 2-3 句话说明根本原因和演化路径，不超过 250 字。

 ## 风险评估
-按严重程度列出风险项及可能后果。
+只列最关键的风险项及其后果，不超过 200 字。

 ## 整改建议
-按紧急程度列出整改措施。
+按紧急程度列 2-3 条措施，不超过 200 字。

 ## 综合结论
-给出综合安全评价。
+一句话给出综合评价，不超过 80 字。
```

**效果**：

| 指标 | 改前 | 改后 | 变化 |
|---|---|---|---|
| Generate token | 552 | 149 | **-73%** |
| 生成耗时 | 112.4 s | 29.9 s | **-73%** |
| 端到端 | 114.9 s | 32.8 s | **-71%** |
| 出字速度 | 4.91 tok/s | 4.98 tok/s | 不变（硬件上限） |

**原理**：在 5 tok/s 的硬约束下 `耗时 ≈ 输出 token ÷ 5`，
所以**提示词的长度约束直接等于时间**。

## 改动 2：提示词加事实约束

**文件**：同上

**问题**：放开采样随机性后，担心模型编造知识库里没有的部件/现象/风险。

**改动**：

```diff
 [严格指令] 你是一个报告生成器，直接输出报告正文。禁止任何对话、问候、确认语句。
+
+【事实约束】只能使用下方提供的故障信息。禁止编造、推测或补充其中未出现的
+部件名称、故障现象、风险项和整改措施。若某项信息缺失，就略过不写。
```

**效果**：连续 3 次生成的报告各不相同，但**每次都 100% 覆盖知识库内容**
（4 项风险、2 条建议、4 个章节全中）。

**原理**：**采样参数管"有无变化"，提示词管"事实性"** —— 两者分工不同。
想保证不编造，靠的是提示词约束，不是把 temperature 调到 0。

## 改动 3：修复 `top_k = 1` 导致的输出恒定

**文件**：板端 `/userdata/rkllm/flask_server.py`

**问题**：

```python
rkllm_param.top_k = 1          # ← 贪心解码
rkllm_param.top_p = 0.9        # ← 完全失效
rkllm_param.temperature = 0.8  # ← 完全失效
```

`top_k=1` 表示每一步只保留概率最高的 token，**贪心解码**，
导致 `temperature` 和 `top_p` 变成死参数。实测两次相同请求的输出**一字不差**。

**改动**：

```diff
-rkllm_param.top_k = 1
+rkllm_param.top_k = 20
 rkllm_param.top_p = 0.9
-rkllm_param.temperature = 0.8
+rkllm_param.temperature = 0.6
```

选值理由：`top_k=20` 给模型合理的表达变化空间；`temperature=0.6`
偏低（不追求创造性），保证报告的事实性。

**效果**：三次输出各不相同（223 / 211 / 241 字），且都 100% 忠于知识库。

## 改动 4：降低 `max_new_tokens` 防长时间满载

**文件**：板端 `/userdata/rkllm/flask_server.py`

**问题**：原值 4096，按 4.9 tok/s 算**最长能连续生成 13.6 分钟**。
实测板子在长时间推理时会随机重启/卡死（累计 4 次），
长生成会显著提高触发概率。

**改动**：

```diff
-rkllm_param.max_new_tokens = 4096
+rkllm_param.max_new_tokens = 512
```

选值理由：报告实际只需 149 token，512 有 3 倍余量，
同时把单次推理的 NPU 满载时间压到 100 秒内。

> ⚠️ 若以后放宽提示词让报告变长，**记得同步调大这个值**，否则会截断。
> （曾经设 512 时被截断过一次，因为报告自然长度是 552。）

## 改动 5：打开 RKLLM 性能日志

**文件**：板端启动脚本

**改动**：

```bash
export RKLLM_LOG_LEVEL=1
```

**作用**：RKLLM runtime 会输出分阶段的性能统计，这是**权威数据来源**：

```
Model init time (ms)  4096.65
Stage         Total Time (ms)  Tokens    Time per Token (ms)   Tokens per Second
Prefill       2307.76          223       10.35                 96.63
Generate      112371.60        552       203.57                4.91
Peak Memory Usage (GB)
4.57
```

不打开这个，就只能靠手工掐表，拿不到 prefill / decode 的分离数据。

## 改动 6：修复日志缓冲导致崩溃前数据丢失

**文件**：板端启动脚本

**问题**：排查板子重启时发现，**崩溃前的日志拿不到**。
原因是 Python 的 `stdout` 重定向到文件时是**块缓冲**的，
进程被硬杀/断电时缓冲区内容全部丢失。

**改动**：

```bash
export PYTHONUNBUFFERED=1
```

**作用**：日志实时落盘，之后几次崩溃都能拿到"断掉前一刻"的数据。
